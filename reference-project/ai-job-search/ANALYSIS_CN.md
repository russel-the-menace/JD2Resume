# AI Job Search 能力分析

## 结论摘要

`ai-job-search` 是一个“本地文件 + AI Agent 命令”的求职操作系统，不是一个前端组件库或后端服务。它把候选人资料、岗位抓取、适配度评估、简历/求职信生成、面试准备和投递结果沉淀在本地工作区，通过 Claude Code（以及兼容的 Agent runtime）执行流程。

我们的产品（`remote-jobs` + `puppet-resume` + 根目录 Draftline UI）则是面向终端用户的微信小程序/Web 简历产品，重点是岗位浏览、岗位收藏、JD 文本或截图解析、双语 AI 简历生成、PDF 渲染，以及会员/支付和云端数据服务。

两者在“JD 驱动的简历定制”上高度重叠，但产品边界不同：上游更强在投递全生命周期的 Agent 编排和可审计的本地资料工作流；我们更强在面向用户的交互、岗位聚合、中文/微信生态、多模态入口、PDF 生成和商业化基础设施。

## 当前产品边界（已确认）

本项目暂不引入推荐信、地点/通勤判断、行为画像、职业目标评分或硬约束筛选。默认用户已经选择了这个远程岗位，系统的职责是把事实资料与 JD 对齐并生成材料，而不是替用户决定是否申请。

当前主链路固定为：

```text
候选人事实资料
  + JD 要求解析
  + 自动补足经验 / 自动填充技能
  + 生成前校验
  -> 生成岗位专属在线简历
```

生成约束也已明确：姓名、联系方式、性别等基本信息，以及已有工作经历的公司名由本地数据锁定；职位、起止时间、职责、技能和补足经历允许根据 JD 动态生成，补足公司和岗位默认允许生成。

校验采用双层分工：本地代码负责文件大小、文字长度、字段类型、必填字段、公司名锁定和 JSON 结构等确定性规则；LLM 负责语义判断，例如岗位关键词覆盖、技能相关性和职责自然度。LLM 的“通过”不能直接放行，最终结果必须再次经过本地校验。

当前模型策略优先使用 `gemini-3.5-flash-lite`，失败或输出不合格时先尝试 `gemini-2.5-flash` 和 `gemini-3.1-pro-preview`，全部失败后才使用 OpenAI `gpt-5-mini`。OpenAI 通过独立 provider 适配，只有配置 `OPENAI_API_KEY` 才启用，并复用同一套本地输出校验。

生成阶段的字段规则：已有公司的 `company` 和 `startDate/endDate` 由本地代码锁定；`position` 在第一阶段可按 JD 改写，第二阶段作为两阶段结构契约沿用；`responsibilities` 和技能动态生成。补足经历的公司、时间、职位和职责默认允许生成。

每次生成都是独立的投递证据实例。必须同时保存 `applicationId`、岗位 ID、岗位快照、候选人资料快照、语言和生成后的简历数据，确保同一个岗位重新生成或切换语言时，也能准确知道某次投递使用了哪一份简历。

## 上游能力清单

### 核心工作流

- `/setup`：从 CV、LinkedIn、学历、推荐信和历史申请材料建立候选人画像；支持重复运行并增量补充。
- `/scrape`：调用职位门户技能搜索岗位、去重，并按候选人画像展示匹配结果。
- `/rank`：批量获取并评分岗位，输出优势、缺口、截止日期和淘汰原因。
- `/apply`：解析 JD，评估匹配度，生成定制 CV 与求职信，由 reviewer agent 复核后修订。
- `/interview`：基于具体岗位、已提交材料和面试阶段生成准备包，并进行模拟面试。
- `/outcome`：记录面试、拒信、offer 和沉默；归档每次申请所用的岗位、CV 和求职信，并生成跟进/感谢信草稿。

### 扩展能力

- `/expand`：从候选人已提供的 GitHub、作品集、Kaggle、Google Scholar 等公开链接补充技能证据。
- `/upskill`：基于岗位缺口生成技能热力图、学习计划和资源建议。
- `/html-report`：从 CSV 和申请归档生成离线漏斗/状态/行业报表。
- `/notion-sync`：单向同步到 Notion，仓库文件仍是事实来源。
- `/gmail-sync`：读取 Gmail 状态信号，批量提出待确认的 tracker 更新，不自动替用户做最终决定。
- `/add-portal`、`/add-template`：扩展新的职位门户和 CV/求职信模板。
- `salary_lookup.py` 与转换工具：可选的薪资基准数据处理。
- 安全与质量控制：岗位内容被视为不可信输入；LaTeX PDF 编译、视觉检查、文本层/ATS 检查，以及技能 lint 和安全 guard 测试。

### 已提供的门户技能

Jobindex、Jobnet、Akademikernes Jobbank、Jobdanmark、LinkedIn 公共职位和 Freehire。门户实现偏丹麦市场，LinkedIn/Freehire 更通用。

| AI 定制简历 | LaTeX CV，按岗位改写并 reviewer 复核 | Gemini 改写经历/技能，生成中英文简历 | 高度重叠，方法不同 |
| 求职信 | LaTeX 求职信模板与生成流程 | 当前未见同等完整的求职信生成/归档能力 | 上游独有/待补 |
| PDF 质量与 ATS | 编译、页数/布局、文本层与关键词检查 | Puppeteer 高保真 PDF；有生成重试与模板渲染 | 部分重叠，上游 ATS 验证更明确 |
| 岗位聚合/搜索 | 6 个门户 CLI、去重、`/scrape`、`/rank` | 岗位列表、搜索、精选岗位、收藏；服务端搜索接口 | 高度重叠，但数据源和部署方式不同 |
| 岗位收藏/投递追踪 | CSV + 申请归档 + `/outcome` | saved_jobs、生成简历关联；未见完整申请状态漏斗 | 部分重叠，上游生命周期更完整 |
| 面试准备 | `/interview`、STAR 映射、模拟面试 | 未见对应产品流程 | 上游独有 |
| 技能缺口/学习计划 | `/upskill` | 未见对应产品流程 | 上游独有 |
| 公开资料扩展 | `/expand` | 有简历导入/个人资料，但未见公开来源证据采集 | 部分重叠 |
| 中英文支持 | 工作流语言/国家无关，模板可扩展 | 中英文简历、微信端 i18n、岗位原文保留策略 | 当前项目更产品化 |

| 数据形态 | 本地 Markdown/CSV/PDF，用户可审计 | 云端 MongoDB/微信云能力 + 本地 Web storage | 架构互补 |

## 不应直接合并的部分

1. 上游 `.claude/commands` 和 `.claude/skills` 是 Agent 指令，不是 React 页面或 Node API；直接复制到 `src` 不会产生可运行功能。
2. 上游职位门户 CLI 依赖 Bun、各门户访问规则和丹麦市场 URL；不能假设适用于我们的岗位数据服务或中国/全球市场。
3. 上游的 `documents/`、tracker、Gmail/Notion 状态包含个人数据边界；只能借鉴数据模型和审批原则，不应把个人样例带入产品。
4. 上游 LaTeX 质量链与我们的 Puppeteer 渲染链是两条不同的文档生产路径，应该先比较输出质量和 ATS 结果，再决定是否引入。

## 建议的借鉴优先级

### P0：最值得产品化

- 引入“岗位匹配评分 + 优势/缺口解释”，作为生成简历前的可见步骤。
- 增加申请生命周期状态：已收藏、已申请、面试中、Offer、拒绝、无回复，并保留每次投递的 JD/CV 快照。
- 在 PDF 生成后增加 ATS 文本层检查和岗位关键词覆盖报告，且明确不虚构技能。

### P1：形成差异化闭环

- 增加求职信生成、版本管理和与岗位绑定的归档。
- 增加面试准备包：岗位重点、STAR 经历、已提交材料回顾和模拟面试。
- 增加技能缺口分析与学习计划，复用现有岗位和简历数据。

### P2：基础设施借鉴

- 把“岗位内容是不可信输入”的安全约束写入服务端提示词和抓取流程。
- 借鉴上游 thin-pointer 设计：将岗位评估、生成、归档规则拆成版本化策略，而不是散落在 UI 事件处理器中。
- 保留本地导出/离线报告能力，作为云端产品的可审计备份。

## 引入后的验证

快照本身不参与现有构建。当前根目录构建和类型检查仍只覆盖 Draftline Vite 应用；上游独立验证需按其 `SETUP.md` 安装 Python/Bun/LaTeX 后运行其测试与 lint。
